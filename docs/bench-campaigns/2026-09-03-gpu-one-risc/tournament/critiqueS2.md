# Seven axes

## 1. Risk surface

**RS-1 — Card 4.1 cannot execute a single step as written; every one of its N1–N6 is unreachable.** 4.1 sets `symbols = [new_count, bucket]` (`generate.rs:1391`) but its blast list covers only `build_position_inputs` (`:1304-1309`), `named_blocks` (`:1313-1334`), `symbols` (`:1391`), `spec.rs:2336-2865` and `bind.rs:3053-3059`. The KV leaf extent is `Extent::Symbolic(1)` (`spec.rs:6217-6244`, verified verbatim), so `expected = element_count(shapes.of(node))` becomes `bucket × kv_heads × pairs`, while `found = block_element_count(block)` is still `cache.k_even.len()` = `cached_len × kv_heads × pairs` (`generate.rs:646-652`, `LayerCache::append` = 3× `extend_from_slice` `:637-641`). The plan's own hard edge ("4.1 precedes 5.3", line 997) is therefore backwards for the only thing that makes 4.1 runnable.

**RS-2 — Card 1.1's census line does not compile.** The card writes `counter!(ROUTE_DISPATCHES[route as usize], 1)` with `pub enum Route { …, Declined(DeclineReason) }`. Rust permits `enum as usize` only for unit-only enums; `Declined(DeclineReason)` is data-carrying, so this is E0605. `counter!` itself takes `$instrument:expr` (`proxima-telemetry/src/metric/mod.rs:36-39`) and would accept an index expression, so the macro is not the obstacle — the cast is. No index mapping is stated anywhere on the card (see hypothesis f).

**RS-3 — Card 4.2's arena breaks a documented readback invariant that the card never opens.** `finish`'s readback carries an explicit comment at `metal.rs:2360-2364`: *"an output node's buffer is always freshly allocated by `encode_op` at offset 0 — only a weight INPUT can carry a nonzero offset, and a weight is never a program output — so reading from the buffer's own start is always correct here."* 4.2 replaces "freshly allocated by `encode_op`" with "bound from an arena" and hardcodes `device_buffers.insert(bound.node, (output, 0))` (`:2249`) unchanged. Any arena that sub-allocates within one buffer — the natural way to meet the card's own 40 MB cap under liveness partitioning — makes that `0` a lie and readback silently returns another op's data. 4.2 lists `:2249` in its opens but never `:2358-2378` or this comment.

**RS-4 — 4.1 needs a `ScalarOp` the closed set does not have, and the guard that would catch it does not cover `ScalarOp`.** `op.rs:60-78` is 17 variants: `Identity, Add, Subtract, Multiply, Divide, Maximum, Minimum, Negate, Reciprocal, Exponential, Logarithm, SquareRoot, Tanh, Erf, Greater, Equal, Select`. **No `GreaterEqual`.** Its own doc at `op.rs:51-53` reads *"Closed on purpose, and it is the one closed set in this crate that stays closed."* Card 0.11's exhaustive-match guard is written for `Op` (5) and `BoundOpKind` (4) only; the plan's non-negotiables (line 30) likewise omit `ScalarOp` and `IndexMap`. So the one variant this plan actually reaches for is the one variant the plan's own tripwire cannot see.

**RS-5 — 0.14 / 7.6 / 7.7 fingerprint private state.** `struct Prepared` is private (`omega/src/metal.rs:859`) with `resolved: Vec<BoundOp>` private (`:864`); `Plan`'s fields are all private (`:313-325`); `cpu.rs:280` `struct Prepared<'block>` likewise. `grep "pub fn resolved|pub resolved"` = 0 hits. The card puts its test in `omega/tests/` (line 325: *"`omega/tests/` gains one file"*) — an external crate that cannot see any of it. Capturing "the plan after `metal.rs:1013`" and "after `cpu.rs:358`" requires new public accessors on two crates; the card's blast radius says "one pure function + one test file."

**RS-6 — 0.6's quarantine loop writes all ten worktrees into one directory.** The command at lines 202-203 is `sh -c 'mkdir -p '"$R"'/$wt-untracked/$(dirname {}); …'`. `$wt` sits inside the single-quoted fragment, so the outer shell never expands it and the inner `sh` has it unset — every worktree's untracked files land in `$R/-untracked/`, overwriting each other. # Hypotheses

**(a) `"*.write_row"` — FOUND, and worse than named.** `grep -rn write_row` over the repo returns 8 hits, all unrelated (`proxima-model-interop/src/capability.rs:208` is a formatting helper; the rest are inside the torch venv). Nothing enforces it. **A structural proof is possible in principle but impossible for 5.1's expression as written.** `IndexMap::scatter(indices: NodeId, …)` (`map.rs:175-198`, read in full) takes any node; `map.rs:100-108` requires only "a backwards reference with an integer DType." An indices node built as `Elementwise{Add, [Iota{extent}, broadcast scalar]}` — the exact construction `causal_mask` uses for its two `Iota`s (`spec.rs:823-845`) — is strictly monotonic by construction and checkable at bind time from the `Op` graph: coefficient-1 `Iota` plus a loop-invariant term ⇒ injective. **But 5.1 does not produce that structure.** 5.1's expression names `indices = "kv_cache.{l}.write_row"` and 5.3 confirms it is *"pushed into `named_blocks` beside `"eps"`"* — i.e. an `Op::Input` leaf whose contents arrive from the host at run time and are opaque to `bind`. For that form no structural proof exists at all, which is why the card fell back to a name. The fix is a different expression (Iota + `cached_len` scalar, which 4.1 already adds), not a different check — and no card writes it.

**(b) `GreaterEqual` — FOUND, not in `ScalarOp`, composition not stated.** `op.rs:60-78` = 17 bodies, enumerated above; `grep GreaterEqual` over `proxima-tensor/src omega/src` = **0**. Arity table `op.rs:100-106` and `is_associative` `:112-117` confirm the closure. The needed composition is `Greater` with swapped operands feeding the existing `Select`/`NEG_INFINITY` broadcast (the `causal_mask` shape at `spec.rs:823-845`, `ScalarOp::Greater` at `:841`), or `Greater(iota, cached_len−1)` with a second leaf. **The card states neither**, and its "zero new variants" claim (line 524) is checked by 0.11's guard, which does not cover `ScalarOp`.

**(c) RoPE and `is_future` — NOT broken; the true `cached_len` still flows host-side.** `build_position_inputs(new_ids, start_position, head_dim, rope_freq_base)` is defined at `generate.rs:799-827`; `start_position` is used only at `:813` (`let position = (start_position + offset) as f32`) to fill `cos`/`sin`, whose extents are `new_count * pairs` = symbol 0. It is called with the true `cached_len` at `:1304-1309`, and `apply_serving_config(serving_config, cached_len + new_count)` at `:1298` also uses the true value. `cached_len += new_count` at `:1559` is untouched. So RoPE positions are host-computed and symbol-1-independent, and `causal_mask`'s two `Iota{extent: Symbolic(0)}` (`spec.rs:823-845`) mask only within the new-token window `s,w` — exactly as `spec.rs:2303-2319` states. Bucketing symbol 1 therefore breaks **neither**; it breaks only the untested assumption that the whole cached range is valid, which is what 4.1's tail mask addresses. The card's diagnosis of *what* breaks is right. What it misses is RS-1: the buffer that feeds symbol 1.

**(d) `AlignedBuffer` page rounding — the hazard 5.3 defends against does not bite; a different one does.** Per layer per token: `k_even` = 8 kv_heads × 64 pairs = 512 f32 = 2048 B, `k_odd` the same, `v` = 8 × 128 = 1024 f32 = 4096 B; ×32 layers = 262,144 B/token, reproducing R13's measured slope exactly. `AlignedBuffer::new` rounds to `element_bytes.next_multiple_of(page_size).max(page_size)` (`align.rs:78-79`) with a 16,384 B page. `capacity × 2048` is a page multiple iff `capacity % 8 == 0`; `capacity × 4096` iff `capacity % 4 == 0`. **At both planned values (256 and 4096) no rounding occurs and `buffer.len()` equals the request**, so 5.3's "derive `capacity_elements` from `buffer.len()`" is a no-op there and its cited conflict-6 resolution is defending an empty case. The disagreement that *does* occur is 4.1's: the symbol is `bucket = div_ceil(cached_len + new_count, 256) × 256` (256, 512, 768 …), not `capacity_tokens` (4096). `found == expected` therefore holds only if `bucket == capacity` at every step — which would mean a 4096-wide attention reduce from token 1 and defeats 4.1's own KV-cost argument. **5.3's headline claim ("the validators never changed, because the leaf extent IS the capacity") is false for the bucket 4.1 actually computes.**

**(e) The fingerprint diff — FOUND; a per-op vector is required and is not stated.** 0.14 defines `pub fn fingerprint(plan: &[BoundOp]) -> u64` (line 320): one FNV-1a-64 over the whole plan. Two `u64`s admit exactly one predicate — equal or not. The card nonetheless requires (i) "a companion always-green test asserting the **difference is exactly the packed operands' strides**" (line 321), (ii) a kill on "the diff includes a node **not** in `packed_operands`" (line 323), and (iii) 7.7's gate printing "the node-set diff" (line 790). All three need a per-op fingerprint vector (or a field-wise structural comparator returning `Vec<NodeId>`); neither is in the field list, the signature, or the blast radius. Compounded by RS-5: both capture points are behind private structs.

**(f) `[Counter; 10]` / `route as usize` — FOUND, does not compile.** Enumerated variants: `Elementwise, Scan, Iota, Constant, ReduceSerial, ReduceCooperative, ReduceRowBlockedPacked, ReduceTiledGemm, ScatterReduce, Declined(DeclineReason)` = 10, so the array width is right, but the index mapping is **stated nowhere** and `route as usize` is illegal on a non-unit-only enum (E0605). Additional consequences: all `DeclineReason`s collapse to one slot, and that slot is structurally always 0 (OB-2). `Counter` is non-`Copy` (`counter.rs:12-17`), so the static needs ten distinct named initializers plus ten snapshot fields (OB-1).

**(g) Per-op-mode ranking — the +7.3% is common-mode, but there is no batched arm and the deletion precedes it.** The inflation R13 records (Σ 61.082 vs batched 56.93) comes from one command buffer per op (`metal.rs:654-761`); at rung 3's seven weight families (225 ops × ~197 µs) a ~2.4 µs per-buffer floor is ~1.2% — and because rung 2 pins both arms to the same `ReduceRowBlockedPacked` count, **that term cancels between arms**. So the inflation itself is not the inversion risk; the risk is that per-op mode inserts a full commit/wait between every op, removing all inter-op overlap, and that `execute_plan_op_timed` runs its **own** upload path (`:664-690`) rather than `execute_plan`'s (`:457-491`). **There is no batched confirmation inside 2.3** — its commands are three `<G3 MILLI>` arms — and per HC-4 no batched per-family number exists in the tree at all. The bench-rung check lives in 2.4, whose commit deletes the losing body (O-6). The correct sequencing is a batched `gpu_exec_ms` A/B before the deletion, in 2.3.

**(h) The arena vs `insert(node,(output,0))` and readback — the insert works; readback is unsound in the sub-allocating form, and outputs are protected only by accident.** `device_buffers` is `BTreeMap<NodeId, DeviceBuffer>`; two nodes mapping to the same `MetalBuffer` is mechanically fine (Metal objects are refcounted), so `:2249` still works for **whole-buffer** sharing. Readback is safe from output-aliasing because `bound_op_retirement` (`metal.rs:1128-1147`) excludes `effective_outputs` by construction (`if !outputs.contains(&node)`), so an output's position can never be reused by a partitioner built on it — but 4.2 cites `bound_op_retirement` only as a **test oracle** (line 552), never as the constraint that makes the partition sound, and never states that outputs are pinned. The genuine unsoundness is the offset: the moment the arena sub-allocates within one buffer to meet its own 40 MB cap, `(output, 0)` is wrong and `finish` reads from the buffer's start (`:2358-2378`), against the invariant spelled out in the comment at `:2360-2364`. Add HC-2: 5.3 changes the output set the whole argument rests on, one card later.

**(i) `depends_on` — NO cycle, NO dangling id.** All 49 cards checked edge by edge. Every referenced id exists (`0.1–0.14, 1.1–1.3, 2.1–2.4, 3.1–3.3, 4.1–4.3, 5.1–5.4, 6.1–6.2, 7.1–7.7, 8.1–8.3, 9.1–9.2, 10.1–10.4`). The only backwards-numbered edge is `10.2 depends_on 10.3`, which is not a cycle (10.3 depends on 3.1, 6.2, 1.3). Branch names: 49 unique `gpu-risc/NN-slug`, no collision with R15's existing list. Card count is **49**, not the 45 the round-2 tally recorded. The prose "hard edges" paragraph (line 997) agrees with the diagram; the "critical path" line does not (O-4).

**(j) Can 5.3 land before 4.1's bucketing is promoted? NO — and "land" is never separated from "promote to default" for 4.1.** 5.3 `depends_on 5.2, 4.1, 4.2`, and 5.2 `depends_on 5.1` which `depends_on 4.3`, which depends on 4.2 → 4.1. There is no path to 5.3 that does not pass through 4.1, and RS-1 makes 4.1 unrunnable without 5.3's buffer change — a genuine two-card cycle in the *code*, invisible in the `depends_on` graph. # The three most consequential new findings

The plan's spine fails on arithmetic and on execution before any of its design questions matter. **First, card 4.1 cannot run a single token**: it sets symbol 1 to the bucket while `LayerCache` (`generate.rs:621-656`) still hands a `cached_len`-sized `Vec`, so `found != expected` at `metal.rs:991-1000` and `cpu.rs:346-356` on step one — the card that pads the buffer is 5.3, which depends on 4.1, and 5.3's own "found == expected by construction" is the mirror of the same error, since `bucket` (256, 512, 768 …) is never `capacity_tokens` (4096); the page-rounding hazard 5.3 spends a paragraph defending against does not even bite at the planned capacities, because `capacity × 2048 B` is already a 16 KiB multiple whenever `capacity % 8 == 0`. **Second, the plan's single board-level prediction is unreachable from its own terms**: 4.3 predicts `[33, 43] ms` while the components it cites — `gpu_exec [43.5,45.5]` plus orchestration `[5.5,6.2]` — floor at 49.0 ms before 4.1's own pre-registered `+[15,25]`, so 4.3's `3.0x` kill will fire on a tree behaving exactly as designed, and 4.1's `[63,72]` band is likewise below its own predecessor's arithmetic (`[67.6, 79.8]` from 3.3's `[54.5,56.5]`). **Third, three cards do not compile or cannot reach their subject**: `counter!(ROUTE_DISPATCHES[route as usize], …)` is E0605 on a data-carrying `Route::Declined`; 4.1's `GreaterEqual` is absent from a `ScalarOp` set whose own doc (`op.rs:51-53`) calls itself the one closed set that stays closed, and 0.11's cardinality tripwire guards `Op` and `BoundOpKind` but not `ScalarOp`; and 0.14/7.6/7.7 fingerprint `Prepared.resolved`, private at `metal.rs:859-864` and `cpu.rs:280`, from a test the card places in `omega/tests/`.
