## Existing primitives fit check

- `StaticBoundedQueue` fits the fixed-capacity, no-allocation handle storage in `unified_scheduler.rs:12-13,24-25`; its core source is `proxima-core/src/ring.rs` (the requested `pipe/bounded.rs` is a re-export, `proxima-primitives/src/pipe/bounded.rs:1-16`). The scheduler's shared capacity check and two-queue fairness policy still need orchestration; replacing it with heap `BoundedQueue` would not improve the fixed-capacity tier.
- `BoundedQueue`/`StaticBoundedQueue` family fits explicit overload semantics, but `DropOldest`/best-effort does not fit the observed admission contract: enqueue errors on full at `unified_scheduler.rs:48-58`; no type-level requirement forbids a drop policy, so this is a semantic contract choice, not a proof of inapplicability.
- `Filter` can model a pure admission predicate (`proxima-primitives/src/pipe/filter.rs`, `examples/filter/main.rs`), but capacity admission mutates one of two queues and reports a full condition, so Filter alone is not a replacement for `enqueue`.
- `DemandGate` is a readiness/dormancy gate (`proxima-primitives/src/pipe/demand.rs`, `examples/gate/main.rs`); scheduler readiness currently returns `Idle` synchronously and stores future-ready handles, with no producer awaiting readiness. It can gate downstream dispatch if a caller needs SHED/WAIT/BALANCE semantics; no such production callsite was found.
- `FanIn` merges ready `In=()` sources and terminates via `Exhausted` (`proxima-primitives/src/pipe/fan_in.rs`, `examples/fan_in/main.rs`). The target has two priority classes, a batch drain, and an explicit bounded decode service interval; current `FanIn` is not that weighted batch policy. There is no `const`/trait constraint preventing adaptation, so do not claim type-level impossibility.
- `Signal` supports sticky one-shot completion and `Signal::child` cancellation (`proxima-core/src/signal.rs`, `examples/signal/main.rs`, `examples/cancellation/main.rs`). Current cancellation is a stream boolean plus queue removal; no Signal is composed at `unified_stream.rs:579-590`. It is a candidate for cooperative notification, not a drop-in queue removal mechanism.
