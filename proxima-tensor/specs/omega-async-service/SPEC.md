# omega-async-service

status: draft
owner: brian
created: 2026-10-12

## problem

A Prime task awaiting `BackendRuntime::evaluate_async` for one Omega CUDA graph must allow exactly one unrelated ready task on the same Prime core to complete before the controlled owner releases that graph, while preserving the hand-derived graph output and typed errors, keeping accepted plan/input storage alive through retirement, and avoiding repeated resident-payload byte scans for an unchanged immutable `LoadedModel` owner.

## refutation condition

A trace in which a Prime future poll calls CUDA synchronization, an accepted job or plan is dropped before GPU work retires, queue saturation loses a job, a stale plan is reused after cache eviction, an async result differs from the same plan's synchronous literal output, a changed immutable owner reuses old resident bytes, or the generic borrowed-input path misses an in-place mutation refutes this design.

## architecture

### owner and lifecycle

`CudaGpuService::start(ServiceLimits)` creates a dedicated `ProximaBackgroundPool::with_threads(1)` and starts exactly one long-lived owner loop with its typed `spawn`, retaining the returned future as its join handle. The service is implemented in `proxima-model-interop`, which already owns the optional Prime and Omega integration dependencies; the worker owns `CudaDriver` and registered `CudaPlan`s. This one-thread pool is owned only by the GPU service; it is not the pool Prime uses for ordinary CPU background tasks. Prime tasks hold cloneable service handles and await results on Prime's per-core executor. The owner receives commands through Proxima's bounded `proxima_primitives::sync::mpsc` channel using its std-gated blocking receive, and processes one CUDA job through completion before the next. The service remains an Omega adapter; queue capacity, wakeup, and close/drain mechanics stay in the reusable channel and background-pool primitives.

`shutdown().await` first closes admission and the bounded command sender, drains every command already accepted by the channel, awaits the worker result, and drops the dedicated pool. A handle drop only drops interest in a result. The service owner must explicitly await shutdown before its final drop from a Prime worker; a fallback Drop closes the command sender so the worker exits, but the Drop path is not a substitute for the async drain contract. The dedicated pool keeps CUDA waits off both Prime executor cores and the application's general CPU background pool. Prime's background task receiver already wakes the awaiting task when its producer completes.

The command sender is the arbitration point for Proxima jobs submitted through this process-local service. It does not coordinate another process such as llama.cpp; comparative benchmarks run each contender under the same device setup without overlapping GPU work.

### resident weight identity

`SharedWeights` is immutable after model load and shared by model clones through `Arc`. Its async generation path carries a clone of a stable identity token into `BackendRuntime`; the runtime retains that token for as long as cached resident copies exist. A pointer-equal token is sufficient because `SharedWeights`' resident names and source slices are immutable and derived from the same owner. The fast path skips resident-vector construction, source-identity collection, and the per-byte content walk. A different token invalidates and recopies, even if its bytes happen to compare equal. The public generic borrowed API does not assert immutability and therefore preserves its exact content comparison, including same-address mutation detection. If an untrusted source replaces cached data, clear the trusted-owner token so a later model-owned call must establish its cache again.

The abandoned alternative was to replace exact comparisons globally with pointer/length checks: the existing generic async API accepts borrowed, mutable slices, so the same address can contain different bytes. Hashing or SIMD comparison was also rejected because it still reads the resident payload on each graph evaluation. The measured baseline harness and raw records are in `measurements/resident-payload-match-versailles-2026-10-13.txt`; this is a synthetic CPU comparator workload, not a model-serving result.

The post-change comparator capture is `measurements/resident-owner-identity-local-2026-10-13.txt`. It pairs the exact content helper and repeated `Arc::ptr_eq` calls on one Apple M1 Max host, with five process runs and 25 retained samples per condition. This host differs from Versailles, so those timing records are not a before/after comparison and do not establish end-to-end serving impact. The mechanism itself is checked by AC21-AC24 counters and mutation controls.

### admission and input ownership

The public execution path is a composed Pipe call: `GpuCapacityGate.and_then(CudaExecutionPipe)`. `GpuCapacityGate` uses Proxima's reusable weighted `CreditGate` Pipe for job and byte limits; its output is `AdmittedGpuJob`, carrying the RAII reservations into the worker command. `CudaExecutionPipe` has `In = AdmittedGpuJob`, `Out = Evaluated`, and `Err = GpuServiceError`; it sends the already-admitted command through a bounded FIFO transport to the dedicated owner and awaits the wakeable result. This makes both capacity waiting and GPU completion ordinary awaits within one composed Pipe call.

The `CreditGate` is implemented once in `proxima-primitives`, where the existing backpressure family lives. `BatchSource` credit is a synchronous consumer pull bound; the service needs a producer call to await admission and carry its permit through cancellation-safe worker retirement. `Demand`'s closed behavior is a successful no-op and would consume/drop a result-producing inference input. `Filter` rejects immediately, while this service contract waits for capacity. The bounded MPSC channel supplies async producer backpressure and wakes the dedicated receiver; no hand-written queue or park protocol is added in the adapter. `max_jobs` and `max_owned_host_bytes` are positive configured limits; no accepted evaluation is dropped. A completed output retains its credit until taken or discarded. No busy-yield or blocking send occurs on a Prime worker.

The current `LoadedModel<'file>` and `QuantizedBlock<'_>` borrow checkpoint/input bytes, so their borrows cannot cross into the background worker's `'static` task. `OwnedBlock` is the concrete transfer: F32 and I32 copy `4 * len` bytes; Packed copies `len`; names copy into `Arc<str>`. At model registration the service builds one immutable owned weight set from `BoundWeights`, sharing its `Arc` payloads across future jobs. Decode-step activations and state are copied once per accepted job. Registration rejects a one-time model copy that exceeds the service byte ceiling before committing it. The current resident-source address key must refer to the service-owned weight allocation for repeated CUDA reuse. This first implementation pays and reports the one-time weight copy; a shared-mmap loader contract is a separate change.

### CUDA completion

The owner invokes the existing checked `CudaPlan::execute_named` on its dedicated blocking worker. That method validates inputs/resources, uploads data, enqueues kernels, synchronizes the CUDA stream, performs fault checks, reads requested outputs, and returns typed failures before the owner publishes completion. The service does not need a CUDA event callback: the Prime task awaits a futures one-shot, and the dedicated worker is the only thread that waits for the GPU. A dropped receiver suppresses delivery only: the owner still completes or fails the CUDA operation, retires the command, and releases one credit. Device failure closes admission and fails queued jobs without attempting another launch on a poisoned arena. Async planning carries the same runtime configuration and exact-activation choice as sync planning, or refuses the unsupported mode before device work.

### serving cache boundary

`BackendRuntime::evaluate` and `evaluate_segment` currently get `&mut Plan` from `plans`/`segment_plans` and call synchronous execution. Under the CUDA async feature, `BackendRuntime::evaluate_async` is added as the owned handoff boundary. It has the same graph, symbol, named-input, output-root, residency, expert-source, and numeric-policy meaning as `evaluate`, but resolves an async CUDA plan lease, copies borrowed input blocks into the owned job, calls the composed capacity-gate/execution Pipe, and returns its awaited `Evaluated` result or typed `InteropError`. The returned future may borrow `BackendRuntime` and caller inputs until polled; the worker command and plan are owned and `'static` after the gate accepts the job. This is graph evaluation, not a new synchronous fallback hidden in the async method. The existing sync `evaluate` remains available for current synchronous callers and non-CUDA engines.

CUDA cache entries become `CudaPlanLease { service, plan_id, generation }`; the concrete `CudaPlan` lives only in the service. Cache hit reuses the id and increments the same hit counter. On a miss, the caller transfers an owned graph request to the service owner; that worker builds the `CudaPlan`, registers it, and returns a lease. Shape misses and exact program changes queue retirement before registration of the next graph. Explicit stream-program invalidation also moves leases to the pending retirement list, which the next async evaluation drains before registration; service shutdown drops all remaining owner plans. Accepted jobs retain the generation until completion. Stale ids fail before launch. The serving owner supplies the service handle explicitly. Capacity wait and service closure preserve typed error meaning; there is no synchronous fallback. CPU, Metal, and wgpu paths do not enter this service.

### decisions

| decision | chosen | why not the alternative |
|---|---|---|
| execution owner | one dedicated thread supplied by Prime's `BackgroundPool` per CUDA service | a Prime executor task cannot call blocking CUDA synchronization; a shared CPU pool can be starved by a long GPU job |
| overlap | one CUDA job at a time per service | the current arena and resident-source maps mutate during execution |
| admission | a wakeable capacity gate waits without blocking Prime and returns the job only when service closure makes progress impossible | immediate rejection loses work during temporary saturation; `Demand` would turn closure into successful no-op and drop the result-producing call |
| input transfer | one-time copied model weights and per-step owned activation/state blocks | current `LoadedModel<'file>` cannot safely cross a `'static` worker boundary |
| completion | existing checked stream synchronization on the dedicated owner, wakeable result to Prime | polling CUDA events from a Prime task requires extra callback state and still leaves output readback to account for; the isolated worker already owns that boundary |

## out of scope

- Async Metal, wgpu, CPU, and heterogeneous per-operation scheduling.
- A shared-mmap loader ownership change; the first CUDA service counts and bounds its one-time weight copy.
- A throughput or latency verdict without per-job records from named hardware.

## risks

| risk | likelihood | what it costs | what we do about it |
|---|---|---|---|
| one-time model copy exceeds memory cap | high for large models | service cannot start | count exact bytes and reject over-budget registration; retain failure payload |
| device loss leaves owner waiting | medium | shutdown cannot finish | propagate sync failure, close queue, wake receivers, test fake failure path |
| cache eviction races accepted job | medium | wrong output or use-after-free | retired generation stays live until accepted count reaches zero |
| completion wake is missed | medium | Prime task stays pending | test both signal/register orders and the same-core progress control |
