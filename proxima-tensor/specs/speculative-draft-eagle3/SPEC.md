# speculative-draft-eagle3

status: audited
owner: brian bruggeman
created: 2026-09-28
restated: 2026-10-12 against `decode-as-data` R5, R6, R11 (readouts plus a draft descriptor)
restated: 2026-10-12 against owner direction: correctness is lossless output over our own trained draft, not llama.cpp token parity

## problem

proxima cannot select `draft-eagle3` on any model it ships; this sub-spec makes it configuration data on the `decode-as-data` frame and gates it on one measure, that speculative output with greedy acceptance equals the target's own plain greedy decode token for token on all 51 corpus prompts for gemma4 E2B, and for granite 1b when its verify program exists and the draft shape fits granite (RL1), and otherwise a typed refusal, never a silent skip (RL4).

## refutation condition

Written before evidence: if, on gemma4 E2B over the 51-prompt corpus (`proxima-model-interop/examples/data/speculative_corpus.jsonl`), `draft-eagle3` with a randomly initialized draft produces fewer than 51 prompts whose ids equal plain greedy, the tap-and-descriptor design (R2, R3, R4) or the verify and rollback plumbing is wrong and must be redesigned, not tuned -- losslessness is binary, there is no threshold to adjust. Separately, if with the trained draft (`speculative-draft-training`) any of the 51 prompts has `accepted=0`, then R2 is suspect, and it is separated from an undertrained draft by the tap-control run (ACL7): the harness runs the same trained draft twice, once with the true tap rows and once with `--tap-rows-from-prompt 1` (prompt i's rows replaced by prompt (i+1) mod 51's rows), and the statistic is `accepted_total`, the corpus sum of per-prompt `accepted`. R2 is wrong only if AC2 passes and `replaced_accepted_total` >= `true_accepted_total` (`true_gt_replaced=false`); if `true_accepted_total` > `replaced_accepted_total`, the tap carries signal and the zero-accepted prompts are a draft-quality finding for `speculative-draft-training`. The degenerate control (`--tap-rows-from-prompt 0`, replacement by the prompt's own rows) must print `true_gt_replaced=false`, else the statistic measures something other than the tap.

## architecture

Nothing here is a new type. EAGLE3 is a hidden-state tap readout list on the target descriptor plus a second descriptor (the draft) with its own `ServingState`, driven through the four pipes of `decode-as-data` (propose, shape, accept, commit). Its row in that spec's table is "draft descriptor fed by target hidden-state taps | tree | sample-and-match | path gather"; this sub-spec uses the chain shape, and trees are `decode-as-data`'s concern.

- **parse (R1)**: no proxima-gguf change. `MetadataArray::I32(Vec<i32>)` (`proxima-gguf/src/value.rs`) already carries an arbitrary-length signed-int array, and `find_tensor` (`proxima-model-interop/src/bind.rs:298-304`) looks up any tensor name with no allowlist. The gap is that nothing reads the `eagle3.*` keys or looks up the `fc`/`d2t`/`enc.output_norm`/`attn_norm_2` tensors. A family profile TOML for the `eagle3` `general.architecture` value, beside the existing profiles, supplies the layer shape; the keys feed the `ModelDescriptor` (`proxima-tensor/src/spec/descriptor.rs:130-296`) the way the other profiles' keys do. The family name is a key value read at load, never a Rust type.
- **target tap (R2)**: `BoundProgram` carries `hidden_root` and `residual_roots` (`proxima-model-interop/src/lowering.rs:137` and `:141`), copied from the `ForwardProgram` at `lowering.rs:419-420`. The Cached/Bounded engine fills one residual root per layer (`proxima-tensor/src/spec/attention_forward.rs:3014`), but gemma4 does not lower through it: the sliding-pattern header (`proxima-model-interop/src/lowering.rs:277-284`) only dispatches `fn header` to `sliding_pattern::header`, and the `CacheMask::Padded` descriptor it returns is the one at `proxima-tensor/src/spec/gguf_descriptor.rs:170`. Three things are missing before EAGLE3 can tap gemma4: the Padded engine (`proxima-tensor/src/spec/scheduled_cached.rs:1136-1853`) must expose per-layer residual nodes the way the Bounded engine does, the caller must select 3 specific indices (not every layer), and the gather must cover every new position. All three are the readout list of `decode-as-data` R5 (slice 3 there), consumed here; this sub-spec adds no gather of its own.
- **encoder/decoder graphs (R3/R4)** need no new `Op` variant. `Op::Input` (`proxima-tensor/src/op.rs:201-205`) is a named leaf where data enters: an externally supplied float row bound to a decode-step input instead of an embedding-table lookup. The feature concat is `Elementwise` into a wider `Input`-shaped buffer; `fc` and the decoder's attention/FFN projections are `Reduce` contractions. The decoder has a single layer and takes a concatenated input of width `2 * n_embd`; llama.cpp's encoder graph is `src/models/eagle3.cpp:124-146` and its decoder graph is `src/models/eagle3.cpp:151-326`, kept as design references for the layer layout, not as numeric oracles.
- **draft loop (R5/R6/R7)** is the propose pipe configured by the `draft-eagle3` value (R8), with accept as sample-and-match and commit as prefix truncate. llama.cpp's loop is `common/speculative.cpp:738-859` (`draft`) and its accept is `common/speculative.cpp:861-876`; the `p_min` stop, the `n_max` stop and the `n_min` clear in R5 are the branches at `common/speculative.cpp:812-830` and `:855-857`. No closed-enum variant is added: the existing `SpeculativeType::DraftEagle3` (`proxima-model-interop/src/serving.rs:208`) is the config vocabulary.
- **lossless harness (RL1-RL5)**: one example, `proxima-model-interop/examples/speculative_lossless_corpus.rs`, runs plain greedy and the speculative path on the same target for every corpus prompt and prints one `lossless id=... identical=... n_drafted=... accepted=... rejected=... first_divergence=...` line per prompt and one `summary prompts=<n> identical=<n> ... accepted_total=<n> rejected_total=<n> proposed_hash=<16 hex> mean_accepted_per_step=<x>` line (`rejected_total` is the corpus sum of per-prompt `rejected`). Flags: `--corpus <path>`, `--drafter <name>` (`none` drafts nothing and is the zero-work control), `--draft-random <seed>`, `--draft-model <path>`, `--max-tokens <n>`, `--limit <n>` (first n prompts), and `--tap-rows-from-prompt <k>` (with a trained draft, replaces prompt i's tap rows with prompt (i+k) mod N's rows, position p taking source row p mod source length; the harness then runs the true-row arm and the replaced arm, prints each arm's summary tagged `arm=true` / `arm=replaced`, and one `tap_control true_accepted_total=<n> replaced_accepted_total=<m> true_gt_replaced=<bool>` line, where each total is the corpus sum of `accepted`). Its comparator is a pure function over two id sequences, so the controls (RL5) run on synthetic id sequences without a model. This sub-spec creates the example; `speculative-draft-dflash`, `speculative-draft-dspark` and `speculative-draft-mtp` consume it.

### decisions

| decision | chosen | why not the alternative |
|---|---|---|
| correctness oracle | the target's own plain greedy decode, over the 51-prompt corpus | llama.cpp token parity needs a llama-format EAGLE3 draft for the same target, and none exists for E2B or granite 1b; the owner's direction is to train our own drafts, and greedy-acceptance speculation is lossless by construction, so plain decode is the stronger oracle for the property that matters |
| draft source | our trained draft (`speculative-draft-training`); a seeded random draft until it exists | a random draft proves losslessness and plumbing; it cannot prove the tap carries signal, which is why RL2 gates `accepted` > 0 only on the trained draft |
| target family | gemma4 E2B first, granite 1b when its verify program and shape allow (RL4) | the tap diagnosis in this spec is gemma4-specific (its profile alone selects `sliding_pattern`, so it alone lowers through the Padded arm that returns no residual roots) |
| hidden-state tap shape | the `decode-as-data` readout list, all-positions, indices from `eagle3.target_layers` | a bespoke tap type would duplicate the readout list for no new capability (principle 1) and is a technique-named type (`decode-as-data` AC9) |
| decoder input | `Op::Input` bound at decode time, same as token embeddings | a new external-embedding `Op` variant was considered and rejected: `Op::Input` is already an untyped named leaf; g_embd needs a new binding at runtime, not new algebra |
| llama.cpp EAGLE3 quirks (recurrent-target stash, backend top-k offload) | not reproduced | they exist for llama.cpp's own targets and have no proxima target (see out of scope) |

## context

### background

- parent spec `speculative-decode-llama-parity` R11b requires a sub-spec for `draft-eagle3`; today proxima has no path to it -- no family profile is selected by a `general.architecture` value of `eagle3` (profiles are embedded TOML files under `proxima-model-interop/src/profiles/`, none named for it)
- gemma4's lowered program carries no per-layer residual roots (its profile selects `schedule_source = "sliding_pattern"`, `proxima-model-interop/src/profiles/gemma4.toml:6`, whose descriptor is `CacheMask::Padded`, `proxima-tensor/src/spec/gguf_descriptor.rs:170`; `build_forward`'s Padded arm returns `layer_residuals: Vec::new()` and `hidden: None`, `proxima-tensor/src/spec/descriptor.rs:958-959`, so `BoundProgram::residual_roots` and `BoundProgram::hidden_root` are empty for it, `proxima-model-interop/src/lowering.rs:141` and `:137`)
- no EAGLE3 draft exists for gemma4 E2B or granite 1b, and the owner's direction (2026-10-12) is to train our own drafts rather than match llama.cpp's draft zoo; so for a caller of `ServingConfig`'s speculative section (parent R9) `draft-eagle3` is unreachable on every model proxima ships
- the change is configuration data on the `decode-as-data` frame: hidden-state tap readouts on the target (`decode-as-data` R5) plus a second `ModelDescriptor` driving its own `ServingState` (`decode-as-data` R6); it adds no technique-named type (`decode-as-data` AC9)
- the one correctness relation: speculative decoding with greedy acceptance is lossless, so its output must equal the target's own plain greedy decode, token for token; with the chain incumbent ~ plain decode (owner-stated premise, not re-measured here) then speculative == plain decode, a metamorphic relation that needs no llama.cpp draft model
