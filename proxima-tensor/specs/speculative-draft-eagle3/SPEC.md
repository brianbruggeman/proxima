# speculative-draft-eagle3

status: audited
owner: brian bruggeman
created: 2026-09-28

## problem

Parent spec `speculative-decode-llama-parity` R11b requires an audited sub-spec for
`draft-eagle3` before draft correctness can be claimed; today proxima has no path to it at
all -- no `Architecture` impl registers under `general.architecture = "eagle3"`
(`proxima-model-interop/src/architecture.rs:484-572` dispatches purely by that string
against a name-keyed registry, and no such name exists), gemma4's forward program exposes
no intermediate-layer hidden states at any position (`bind.rs:1034-1035` leaves
`hidden_root: None`, `residual_roots: Vec::new()`), and no EAGLE3 draft GGUF for any
proxima-shipped target family exists on this machine, so for a caller of `ServingConfig`'s
speculative section (parent R9) `draft-eagle3` is unreachable on every model proxima ships
-- this sub-spec makes it token-identical to llama.cpp `f1ea20621`'s
`common_speculative_impl_draft_eagle3` (`common/speculative.cpp:455-920`) for the gemma4
target family, the one family both proxima and llama.cpp's own EAGLE3 sidecar list
(`docs/speculative.md:39-40`) support.

## refutation condition

Written before evidence: if, on the target+draft pair named in slice 1, running the ported
`draft-eagle3` drafter through 50 prompts from the parent spec's AC17 corpus produces a
mean of 0 accepted draft tokens per verify step while llama.cpp's own `llama-cli --spec-type
draft-eagle3` on the identical pair, prompts, and seed produces a nonzero mean, the forward-
program design in this spec (the hidden-state tap shape, R2) is wrong and must be redesigned,
not tuned -- the failure is architectural, not a threshold to adjust.

## architecture

Two gaps named first, per the task brief:

- **parse gap: none in proxima-gguf itself.** `MetadataArray::I32(Vec<i32>)`
  (`proxima-gguf/src/value.rs:81`) already carries an arbitrary-length signed-int array, and
  `find_tensor` (`proxima-model-interop/src/bind.rs:250`) looks up any tensor name with no
  allowlist. The gap is entirely on the model-interop side: nothing reads
  `eagle3.target_layers`/`eagle3.target_hidden_size`, and nothing calls `find_tensor` with
  eagle3's tensor names (`fc`, `d2t`, `enc.output_norm`, `blk.0.attn_norm_2`, ...). R1 closes
  this by adding an `Eagle3Arch` the same shape as `Gemma4Arch`/`Qwen35Arch` -- a new
  registry entry, not a proxima-gguf change.
- **hidden-state tap gap: real, on gemma4's forward program.** `BoundProgram` already has a
  field shaped for this -- `residual_roots: Vec<NodeId>`, "one post-layer residual root per
  dense layer, when the forward builder exposes them" (`architecture.rs:140-143`), populated
  today only by `dense.rs:148`'s `layer_residuals`. `gemma4/bind.rs:1034-1035` leaves it
  `Vec::new()`. Three things are missing before EAGLE3 can tap gemma4: (a) gemma4 must
  populate per-layer residual roots at all, (b) the caller must be able to select 3
  *specific* indices (llama's `target_layer_ids`, not "every layer"), and (c) the gather
  must be all-positions (matching `bind_gemma4_all_positions_logits`, `bind.rs:1056-1061`),
  not last-row-only like every other current consumer of `residual_roots`. R2 closes this by
  giving `Eagle3Arch::bind`'s target-tap call a caller-supplied `&[u32]` of layer indices and
  reusing the existing all-positions gather shape from `bind_gemma4_with_last_row_only`'s
  `last_row_only: false` path.

Everything else composes existing primitives:

- **encoder/decoder graphs (R3)** need no new `Op` variant. `Op::Input { dtype, shape, name }`
  (`proxima-tensor/src/op.rs:184-188`) is already "a leaf where data enters" by name, which
  is exactly llama.cpp's `common_batch::set_embd` (an externally-supplied float row bound to
  a decode-step input instead of an embedding-table lookup). The 3-layer feature concat is
  `Elementwise` copy into a wider `Input`-shaped buffer; the encoder's `fc` and the decoder's
  `wq`/`wk`/`wv`/`wo`/FFN are `Reduce` contractions identical in shape to gemma4's own layer
  ops, just with `n_layer == 1` and the concatenated-input width `eagle3.cpp:220-221`'s
  `ggml_concat` names.
- **draft loop (R4-R6)** slots into the parent's closed `enum Drafter` the same way `draft-simple`
  (parent R10) does: a variant holding a second `LoadedModel` plus, here, the target's
  hidden-state-tap handle from R2. No `Box<dyn Drafter>` -- the set is llama's own closed
  enum of speculation types (`common/speculative.h`'s `common_speculative_type`).
- **fixture generator (R9)** is a C++ harness in the same shape as the parent's ngram
  generator (`proxima-tokenizer/tests/fixtures/llama-ngram/`, slice 2 of the parent's
  TASKS.md): compiled against llama.cpp `f1ea20621`, driving a real gemma4 target context
  and the real EAGLE3 draft context through `common_speculative_impl_draft_eagle3` end to
  end, dumping (a) the 3 tapped hidden-state rows per position, (b) the encoder's g_embd
  rows, and (c) the drafted token sequences with their accept-rewind positions, to JSON with
  the upstream commit recorded in the header.

### decisions

| decision | chosen | why not the alternative |
|---|---|---|
| target family | gemma4 only | it is the only family both proxima ships and llama.cpp's supported-EAGLE3-draft list names (`docs/speculative.md:39-40`: `RedHatAI/gemma-4-31B-it-speculator.eagle3`, `RedHatAI/gemma-4-26B-A4B-it-speculator.eagle3`); a Qwen3/Llama3 pair would need a second target architecture this crate does not bind yet |
| hidden-state tap shape | extend the existing `residual_roots` gather to caller-chosen indices, all-positions | a bespoke `Eagle3HiddenTap` type would duplicate `bind_gemma4_all_positions_logits`'s already-working all-positions gather (`bind.rs:1056-1061`) for no new capability -- RISC reuse (principle 1) |
| decoder input | `Op::Input` bound at decode time, same as token embeddings | a new "external embedding" `Op` variant was considered and rejected: `Op::Input` already is an untyped named leaf (`op.rs:184-188`); nothing about g_embd requires new algebra, only a new binding at runtime |
| oracle | llama.cpp `f1ea20621`'s own `common_speculative_impl_draft_eagle3`, compiled into a fixture generator, on the pair from R8 | re-deriving expected g_embd/logit rows from reading `speculative.cpp`/`eagle3.cpp` is principle 14's "from memory" failure; no existing llama.cpp tool dumps `llama_get_embeddings_layer_inp` outside this impl, so the harness calls the same public API the impl calls, not a parallel reimplementation |
| compat check | eagle3-specific (`target_layer_ids_n == 3`, ids in range) | `common_speculative_are_compatible`'s vocab/bos/eos gate is never called from eagle3's own constructor (`speculative.cpp:486-561` has no such call, unlike draft-simple's constructor at `:242-248`) -- copying it would diverge from the incumbent |
| KV/rollback ownership | parent spec's R3a/R3b | eagle3 uses the same `LayerCache::truncate` rollback as every other drafter; this sub-spec owns only eagle3's own deferred-boundary rewind (R5), which is additional per-drafter state, not a KV mechanism |

## out of scope

- Qwen3/Llama3/gpt-oss EAGLE3 pairs -- proxima has no target `Architecture` for those families; gemma4 is the only pairing available today (see decisions table)
- the `norm_before_residual`/`norm_before_fc` RedHat/eagle3.1 variants beyond reading the two optional GGUF bools and branching the two known cases (`eagle3.cpp:24-29`, `:131-134`, `:213-217`) -- no third variant is named upstream
- backend-offloaded top-k sampling (`params.draft.backend_sampling`, `speculative.cpp:526-538`) -- CPU-side top-k=10 sampling only; offload is a performance path, not a correctness one, and llama.cpp itself falls back to CPU on offload failure (`speculative.cpp:531-535`)
- DFlash / dspark (`speculative.cpp:923+`) -- parent R11c/R11d, separate sub-specs

## risks

| risk | likelihood | what it costs | what we do about it |
|---|---|---|---|
| RedHatAI's gemma-4-31B-it target is too large to run repeatedly in CI/dev loop (unlike the parent spec's 2B E2B fixture) | high | slow iteration, possibly needs the 26B-A4B MoE pairing instead, which this crate's MoE gemma4 path must also support | slice 1 records actual download size and picks the smaller of the two named pairs first |
| gemma4's per-layer residual output shape does not line up with llama.cpp's `n_embd` per-layer convention (e.g. gemma4 has a distinct pre/post-norm residual stream) | medium | R2's tap reads the wrong tensor, producing a plausible-but-wrong g_embd that still runs | AC4's fixture comparison is byte/float-tolerance exact, not just "compiles and runs" |
| HF checkpoint format for RedHatAI's speculator does not match either of the two documented formats (SpecForge `LlamaForCausalLMEagle3` / vLLM `Eagle3LlamaForCausalLM`) | low | slice 1's conversion step fails before any proxima code is touched | `convert_hf_to_gguf.py` is llama.cpp's own converter and already declares both formats supported (`docs/speculative.md:24-25`) |
