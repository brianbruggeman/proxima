## open items

- **The bounded engine refuses sinks rather than lowering them (closed by refusal in slice 6).** `CacheMask::Bounded` has no per-layer attention channel beyond the mask window, so `build_forward` now returns `UnsupportedInBuilder { feature: "attention sinks (this engine has no per-layer sink channel)" }` when the schedule carries the knob (`proxima-tensor/src/spec/descriptor.rs`, the Bounded arm) instead of lowering a program that binds the tensor and never adds it to the denominator. Implementing sinks there needs a per-layer channel in that engine, not a flat bool.
- **Three descriptor constructors hard-code the knob off.** `proxima-model-interop/src/recurrent_interval.rs:384` and `proxima-model-interop/src/recurrent_routed_interval/program.rs:74` build their per-layer config with `attention_sinks: false` from hparams that carry no sink presence, and both feed `build_forward` (`recurrent_interval.rs:464`, `recurrent_routed_interval/program.rs:172`). That is the same silent-drop class as the single-range item below: a sink-bearing checkpoint loaded through either reader would lower with no sink leaf and raise nothing. The third is `proxima-tensor/src/spec/descriptor.rs:682` (`gqa_descriptor_from_shape`, the production dense reader reached from `hf_descriptor.rs:53` and `dense.rs:72`); it is the same class and is only closable with a sink-presence field on that shape's input. Whether any sink-bearing checkpoint reaches these readers is unmeasured; the fix is a presence field on the input each one derives from — slice 3's for the gguf header readers, a shape-owned one for `gqa_descriptor_from_shape`.
- **The single-range `metal-output-placement` path has no sink channel at all.** `build_single_range_program` (`proxima-model-interop/src/generate/load_model.rs:1441`) builds `gqa_single_range_cached_forward_program*` from `ModelHparams`, which carries no attention config at all — and that absence of a channel is exactly what makes the drop silent: a sink-bearing dense checkpoint reaching that path lowers a program with no sink leaf and no sink term and raises nothing. Today only `expert_count != 0 → Ok(None)` (`:1445`) keeps it away from MoE checkpoints. Giving it sinks needs `ModelHparams` to carry sink presence — slice 3's reader work.
- **Ordering constraint: slice 3's flag-set must not land without slice 7's term.** Between them a flagged program declares the leaf, binds the tensor, and adds nothing to the attention denominator: wrong logits with no error anywhere. The flag has no production setter today, so nothing is wrong now; the two slices must land on one branch, and slice 12's parity AC is what would catch a split.
- **A flag-on program whose directory lacks the tensor fails at the first decode step, not at load.** Binding is quiet (`bind_program_leaves` falls through to `bind_per_expert_stack`, which returns `Ok(())` for a non-expert-stack leaf: `proxima-model-interop/src/bind_leaves.rs:165-168`, `:439-452`), but the decode step's `missing_program_input` scans **every** `Op::Input` with no consumer test (`load_model.rs:1379-1389`) and returns `InteropError::MissingStepInput { name }` (`generate/decode.rs:5203-5213`). So the failure is loud and named, at serving time rather than load time; slice 9's directory census (AC9/AC27) is what moves it to load time.
- **The slice-6 tests stay synthetic.** The leaf width is asserted at the captured header's `query_heads = 32` for four of the five lowerers (the routed hybrid at its module's synthetic 2), and the `(32,)` shape is measured off `tensor_dir.txt:16`, but no test binds the real flint tensor bytes or its stored f32 values; slice 9 does.
