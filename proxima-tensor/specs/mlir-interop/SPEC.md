# mlir-interop

status: audited
owner: Brian Bruggeman
created: 2026-10-11

Owner direction, 2026-10-11: one generic IR (proxima-tensor's algebra: generic expression, indexing maps, scalar body, schedule separate; the MLIR Linalg / Halide / TVM tradition) lowered by omega to many doors; every door is a proxima pipe with an FSM over its stages; GENERIC; meet or beat the incumbent per door and cell; MLIR "opened up" in both directions, not left as a card. Binding invariant, same day: "these should have all of the same shape: just an fsm x sans-io for omega to build the format." One door FSM lives in omega and is generic over the format; reading is parse, validate, lower, plan, execute; writing is lower, emit, package, verify; stages, errors, plan cache and the walkthrough exist once. A format is exactly two sans-IO pipes (bytes to program, program to bytes) and gets no FSM, no stage enum and no door type of its own. `mlir-opt` is outside the pipe: it is the edge that verifies emitted text, and the oracle. Second invariant, same day: the implementation uses "our favored approach (fsm x sansio | pipe | fsm x sansio... all the nostd, noalloc, zerocopy, zerolock, etc. from /guiding-principles and /disciplined-component)"; the sixteen gates of `/disciplined-component` are counted ACs here (R22 to R31), not a closing checklist.

## problem

omega cannot exchange programs with MLIR: it neither exports the `Op` programs of the real decode steps of granite-3.1-1b-a400m (Q8_0 GGUF, `/Users/brianbruggeman/.ollama/models/blobs/sha256-cd60b3e8bb445d4c05e0b0b99b1bb41e8bb77211b161e783c71931168131df80`, 1422239776 bytes) and gemma4 E2B (Q4_0 GGUF with Q6_K tables, `/Users/brianbruggeman/.ollama/models/blobs/sha256-3646b4c147cd235a44d91df1546d3b7d8e29b547dbe4e1f80856419aa455e6fd`, 3349514112 bytes) as one Linalg-on-tensors module per model that `mlir-opt` 21.1.8 verifies, with a census that names, per op, whether its form is faithful, faithful only after a buffer repack, or absent; nor imports the torch-dialect dump of BAAI/bge-small-en-v1.5 (6303 ops, produced by IREE 3.13.0rc20261011 from the ONNX file pinned in `proxima-tensor/specs/onnx-door/SPEC.md`) through one MLIR reader pipe plugged into the same door FSM as the ONNX reader, with every L2-normalized CLS embedding of the 64-sentence corpus within max abs 1e-5 (`Engine::Cpu`) and 1e-3 (`Engine::Gpu`, Metal) of the output tract-onnx 0.22.4 recorded on the same input tensors at batch 1 and batch 32, and with the median time per sentence at or below tract's recorded median plus max(MAD, 2%) in each of the four engine-by-batch cells, measured by the `mlir_door_bench` example under the parity rounds' bench discipline (interleaved arms, box-load refusal, CoV, resource columns, bound lines).

## refutation condition

Any one of these refutes MLIR interop as present and viable:

1. `mlir-opt` rejecting the emitted module of either model, or its own reprint of the emitted module holding a different op count than `proxima-mlir`'s parse of the same text (R6);
2. the export census (R5) reporting any op of class `none` in either real decode program: such ops have no MLIR form, so export is a paper for them, and the count is reported rather than hidden by the opaque-call fallback;
3. the import census (R8, R9) reporting an unmapped op in the bge-small or MNIST dump, or the mapping needing a new `Op` form, `ScalarOp` or `IndexMap` variant: the algebra would then not be the generic IR for the torch dialect;
4. a sentence of the 64 whose embedding exceeds the stated tolerance against tract's record at batch 1 or batch 32, on CPU or Metal (R12, R13);
5. a `bound` line with `within=false` in the time or memory cells (R19, R20);
6. either MLIR direction needing a stage enum, an error enum, a plan cache or a door type of its own, or the ONNX door tests needing any edit to pass (R1, R14);
7. the vendored dump's op count disagreeing with `mlir-opt`'s own reprint of it (R7): the parser would be wrong and every import row void;
8. the lexer or the emitter allocating in its 100k-iteration hot loop, or `proxima-mlir` failing to build for a bare-metal target at the tier it claims (R24, R25): the sans-IO, no-alloc claim would be false.

Oracles, none sharing code with the path under test: `mlir-opt` 21.1.8 and `mlir-runner` 21.1.8 from Homebrew LLVM (verifier, reprint op counts, and execution of emitted text); hand-derived values (matrix products, softmax, erf, convolution, batch norm, the StableHLO specification's worked examples); the Metal capture records `census_dispatches.csv` of the decode-prefill-parity evidence, which were written by the GPU encoder and share no code with the exporter; tract-onnx 0.22.4's recorded embeddings (`omega/tests/fixtures/bge-small/tract_b1.jsonl`, `tract_b32.jsonl`, recorded as files, never re-run in a gate); the MNIST `t10k` labels; a counting allocator for allocation claims; IREE's `iree-import-onnx` and `iree-opt` as the producer of the real dumps, run once as vendor tools (the dump is the artifact, the producer is not in any gate). Python code of ours is never written or run.

Controls, by kind of check. A comparison against a recorded or vendored external file carries an identity control (the record compared to itself through the same comparison function passes) and a degenerate control (a copy altered in one place fails). A comparison against a hand-derived value carries a degenerate control (the expected value altered fails). A check by an external verifier carries a degenerate control (the checked text altered in one place fails) and an identity control (the verifier's own reprint of the text passes). A counter over source text carries a control (the counter over a string holding one hit returns 1). An allocation assertion carries a control (the counter over a loop that allocates returns a nonzero count). A structural assertion against a constant stated in its own AC (a count, a shape, a file name) carries none. Each control is a counted test case inside its AC.

### the door, once

Today's door is named for ONNX (`omega/src/onnx_door/mod.rs:99` `OnnxDoor`, `stage.rs:18` `DoorStage`, `error.rs:61` `DoorError`, `cache.rs:43` `PlanCache`) and its first three stages call `proxima_onnx` directly (`parse_complete`, `census`, `lower_graph_pinned`). The generalized door holds the same five reading stages and adds the four writing stages in the same enum:

| direction | stage | holds | by | failure |
|---|---|---|---|---|
| read | `Parse`, `Validate`, `Lower` | the reader's intermediate values and then `Lowered` | the format's reader pipe, `bytes + pins -> Lowered`, whose error names which of the three stages raised it | `DoorError` for that stage with the format's own error as source |
| read | `Plan` | `Lowered` and the omega `Plan` | `plan_named` (`omega/src/backend.rs:413`) | `DoorError::Plan` |
| read | `Execute` | the plan and the `Evaluated`, then back to `Plan` for the next batch under the same pins | `execute_plan_named` (`backend.rs:488`) | `DoorError::Execute` |
| write | `Lower` | the program and its `LinalgModule` with per-op classes | the format's writer pipe | `DoorError::Lower` (strict policy only) |
| write | `Emit`, `Package` | text of the body written into the caller's buffer, then the wrapped module | the format's writer pipe | `DoorError::Emit` (including `BufferTooSmall`), `DoorError::Package` |
| write | `Verify` | the bytes and the verdict of the edge | `proxima-mlir`'s own re-parse and structure check; then the verifier edge a caller supplies (tests supply `mlir-opt` at `MlirConfig::verifier_path`) | `DoorError::Verify` naming line and column |

`Lowered` (`proxima-onnx/src/lower.rs:170`: program, initializers, graph inputs, graph outputs) is format-neutral and moves to `proxima-tensor` with a re-export from its old path, so `proxima-mlir` does not depend on `proxima-onnx`. The exact signatures (a `Door<Reader>` and a writer-side instantiation of the same stage enum, and how a reader's error names its stage without a boxed trait object) are slice 1's decision under the constraints of AC1 and AC14; slice 1 first checks whether `origin/main` already carries a generalization and reuses it if so.

### the export, structurally

The algebra's `Elementwise` and `Reduce` are Linalg generic by construction (`proxima-tensor/src/op.rs:191` `Op`, `map.rs:218` `IndexMap`): an operand's `IndexPattern` is an indexing map, the scalar body is the generic body, the iteration space is the iterator list, and the schedule is not in the program at all. So the lowering is a table over the five forms, not an op-by-op translation:

| algebra form | Linalg form | class |
|---|---|---|
| `Input` | function argument `tensor<...xT>` (or `memref`) with attribute `proxima.name` | faithful for an element type in R4's table |
| `Input` bound to a block-quantized codec (Q4_0, Q8_0, Q4_K, Q5_0, Q5_1, Q6_K, ...) | two arguments (quants `iN`, scales `f16`) read through a `floordiv` indexing map, dequantized in the body; attribute `proxima.repack` names the source codec | `repack`: the omega buffer interleaves scale and quants per block, which no strided tensor layout reads in place |
| `Input` of `Fp6E3M2` (6-bit codes under a per-block scale, `proxima-tensor/src/dtype.rs:33`) | the same repack form with the scale tensor | `repack` |
| `Constant` | `arith.constant dense<v>` splat | faithful |
| `Iota` | `linalg.generic` with `linalg.index` | faithful |
| `Elementwise`, affine operand maps | `linalg.generic`, all iterators `parallel`, one `affine_map` per operand (terms to `d_i * coeff`, offset), identity output map | faithful |
| `Elementwise`, `IndexMap::Computed` operand | `linalg.generic` with the index tensor as an extra input and `tensor.extract` of the table in the body | faithful when the gathered axis is within 2^24 (the algebra's own f32-index rule, `map.rs` doc) |
| `Reduce`, `Keep::Reduce`, affine out-map | `linalg.generic`, `reduction` iterators on axes absent from the out-map, output seeded by `linalg.fill` with the `ReduceInit` value | faithful |
| `Reduce`, `ReduceInit::FirstElement` (argmax) | none | `none(first_element_seed)` |
| `Reduce`, `Keep::Scan` | none: Linalg has no prefix scan | `none(scan)` |
| `Reduce`, computed out-map (scatter) | none | `none(scatter)` |

A `none` op is emitted, by default, as a call to a private function declaration of the same tensor types (`func.func private @proxima_opaque_<reason>`), which is valid MLIR that a consuming back end must supply, so the module still verifies; the strict policy refuses instead with a `DoorError::Lower` naming every such op. The census counts either way, so the opaque fallback cannot hide a gap.

Scalar bodies: `Add`/`Subtract`/`Multiply`/`Divide`/`Negate` to `arith`, `Maximum`/`Minimum` to `arith.maximumf`/`minimumf` (NaN propagating, checked against omega's CPU semantics by AC3), `Exponential`/`Logarithm`/`SquareRoot`/`Tanh`/`Erf` to `math`, `Reciprocal` to `divf 1.0`, `Greater`/`Equal` to `cmpf` then `select` of 1.0/0.0, `Select` to `arith.select` on a nonzero condition, `Identity` to a yield.

### the import, structurally

`MlirReader` is `lex -> parse -> structure -> census -> lower` composed with `and_then`; each is a function over borrowed text, none is a pipe of its own that needs an FSM. The lower step walks the module once in program order (a block's definitions precede their uses, the same backwards-only rule `op.rs` states for `Vec<Op>`) with a value environment like `proxima-onnx`'s `Value` (`lower.rs`), and has three outcomes per op: `mapped` (the op becomes `Op`s through a composition core), `host_folded` (the op computes a shape, an index or a flag from pinned dimensions and constants, is evaluated during lowering, and leaves nothing in the program), `unmapped` (reported). The real bge dump holds 6303 ops of 44 names, and most of its volume is host arithmetic over the two dynamic dimensions (`torch.constant.int`, `torch.prim.NumToTensor.Scalar`, `torch.aten.item`, `torch.aten.size.int`, `torch.aten.where.self` and `torch.aten.eq.int` are 3015 of the 6303); that is why `host_folded` is a class of its own and why the pins of `DoorBatch` bind the dump's `?` dimensions.

Composition cores. The torch and StableHLO tables do not restate the ONNX op bodies. The attribute-free core of each composition that both formats need (matmul, softmax, erf, reduce-mean, transpose, broadcast add, convolution, batch norm, layer-norm pieces) is a function over `(NodeId, shape, view)` values in one place, and `proxima-onnx`'s `lower_*` functions and the MLIR tables both call it. Slice 11 moves the cores with `proxima-onnx`'s tests untouched (AC9 compares the program the ONNX path and the torch path build for the same case).

### what the constraints changed (principle 'name a design you abandoned')

- A per-format door (`MlirDoor` with `MlirStage`, `MlirError`, its own cache) was the first draft; the invariant "a format is two pipes" removed it, and the door generalization (R1) is what remains of it.
- An owned-`String` AST was the first parser shape; the no-alloc and zero-copy gates (R25) turned it into `Copy` tokens and `&'a str` views into the input, which also made the parser's hot data a flat arena.
- Emitting from `BoundOp` was the first export shape; the generic-IR frame removed it (the recognizers' outputs are not the algebra), see the decisions table.
- A `Mutex`-guarded plan cache shared by two readers was the first cache shape; lock-free-first (R26) turned it into the door's existing single-writer cache and stateless `Sync` pipes.
- Binding `melior` or LLVM's C API for emission and verification was the first tooling shape; the text-only invariant turned `mlir-opt` into an edge outside the pipe.

### decisions

| decision | chosen | why not the alternative |
|---|---|---|
| a door type per format | none; one door, a format is two pipes | the owner's invariant of 2026-10-11. Answered by writing the call site both ways: before, `OnnxDoor::from_bytes(bytes, &config)` and a hypothetical `MlirDoor`; after, the same `Door` over `MlirReader`. The two lines differ, and a caller can now do what it could not: move a pin-set cache, a stage-attributed error and a walkthrough between formats |
| emit at the `Op` program, not at `BoundOp` | `&[Op]` plus symbols plus named codecs, the arguments of `plan_named` (`backend.rs:413`) | `BoundOp` (`bind/types_layout_boundop.rs:146`) carries the fusion recognizers' outputs (`CachedAttention`, `GatedDeltaNet`, `MoeTopK`, `RoundBatchedReduce`, `CachedSoftmaxWeights`, `ElementwiseTwin`): exporting those would export the recognizers, the opposite of fusion as a pass over the algebra. The unfused program is the generic form, and a consuming compiler fuses it |
| quantized weights | `repack` form with a stated source codec | a faithful in-place form does not exist for interleaved blocks, and silently dequantizing to f32 would change the byte contract; the census counts the repack so the cost of the lane is a number |
| `none` ops | opaque call by default, strict refusal on request, always counted | dropping them would verify a module that computes something else |
| the import dialects | the torch dialect (the dump a vendor tool produces) and StableHLO (the interchange the card names), over one parser | the generic form is dialect-agnostic, so the parser is one; the two tables differ. | weights of the imported model | bound by name to the ONNX file's initializers | the dump externalizes its 198 large parameters as `#stream.parameter.named<"model"::"...">`; their bytes live in an IREE parameter archive, a second format. | `mlir-opt` inside the pipe | no: it is the edge | a pipe that needs a 100 MB external toolchain is not sans-IO; `Verify` re-parses with `proxima-mlir`, and the test supplies `mlir-opt` as the verifying edge |
| text only | no `melior`, `inkwell`, LLVM or IREE crate | the card's non-goal; AC17 counts it |
| parser output | arenas of `Copy` records holding spans; strings are views | an owned AST pays an allocation per name; the principle-11 clauses (borrowed views, zero-copy) forbid it on the hot path |
| lexer scans | `memchr` for the delimiters that end a quoted name, a string, a comment and a line; a 256-entry byte-class table for the rest | hand-rolled byte loops lose to `memchr` by 5 to 20 times on long runs (principle 11); the lexer's `memchr` is its one dependency and is `no_std` |
| pins | the dump's dynamic dimensions bind through `DoorBatch::pins` like ONNX's | the lowering binds concrete shapes (`lower.rs` doc); a symbolic plan is not what the lowering produces |
| reuse audit, internal | the decoder/census/lower pattern of `proxima-onnx` (`census.rs:42`, `lower.rs:229`) is reused as the reader's stage shape; the text emitters `omega/src/msl/emit_and_classify.rs:43`, `omega/src/cuda.rs:183`, `omega/src/wgsl.rs:182` are the precedent for text-out-from-program, and none can be extended because each emits a kernel per `BoundOp` while this emits a module per `Op` program | the audit is also written per module in the log (R29) |
| reuse audit, external | `Cargo.lock` and `fuzz/Cargo.lock` hold no MLIR text crate (AC17 counts 0); `mlir-opt` stays a tool because linking LLVM contradicts the text-only invariant and a 100 MB dependency buys only a verifier that the edge already provides | `memchr` is the one external crate the lexer adds |

- a StableHLO dump of a real model: none is downloadable as a text file (the public `.mlir` models in `iree-org/iree-test-suites` are resnet50, whisper-tiny-en, qwen3-600m and a toy llama, all in the torch dialect, none BERT), and producing one needs the Python torch-mlir exporter; R10 is measured against the specification's examples
- Linalg named ops (everything is emitted as `linalg.generic`), tiling, fusion and any schedule in the emitted text
- consuming the exported module in a back end (hexagon-mlir, MLIR-AIE, IREE): the export is verified by the MLIR tools only
- IREE parameter archives (`.irpa`); the weights are the ONNX file's
- dynamic shapes in export (symbols are bound before emission), quantized-QDQ import, tokenization
- no-alloc operation of the parser, reader and writer: only the lexer is claimed at tier 3; the parser's arenas and the lowering allocate and are counted by the discipline log, not asserted zero
- other doors (GGUF, safetensors, MLX, CoreML): the door frame is the one generic machine, and this spec adds the MLIR format and generalizes the machine only
- changing tolerances or bounds after a measurement; a failing number is reported, not widened
