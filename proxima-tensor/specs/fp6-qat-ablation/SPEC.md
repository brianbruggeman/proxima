# fp6-qat-ablation

status: audited
owner: Brian Bruggeman
created: 2026-10-11

## problem

On this Mac's GPU (Metal, the only machine), a 256-step quantization-aware fine-tune of granite 3.1 1b A400M (bf16 masters dequantized from the Q8_0 checkpoint, bf16 activations, f32 accumulation, ~~f32 compute~~ struck: f32 compute is the interim the owner refused on 2026-10-11 ("why would you accept f32 when a) it's more expensive everywhere and b) we no longer have a real timing"), Adam learning rate 1e-4, seed 17, 4 sequences of 256 tokens per step, 1,024 tokens per step) with e3m2 fake-quant (OCP MX element s1e3m2, f16 absmax scale per 32, straight-through backward) on the 168 expert and attention projection tensors, trained on the first 90% of the paragraphs of `war_and_peace.txt` and evaluated on the last 10%, is measured by these bounds: final held-out loss (64 sequences of 256 tokens) no more than 0.05 nats per token above the same-seed fine-tune with fake-quant off (the control) and below the control's weights quantized to e3m2 after training with no QAT (the ptq arm); positional token agreement of the converted QAT checkpoint against the recorded llama ids (224 positions) no more than `floor(0.02 x 224) = 4` positions below the unconverted control checkpoint's own count; and, before any of that, once omega's Metal path takes any `FloatLayout` as a dtype through one generic implementation and passes parity (R2), the fake-quant-off training throughput (ms per step, tokens per second, peak RSS, peak GPU bytes, CoV) measured at one layer and at all 24 layers with masters and activations in the `FloatLayout::BF16` instance and accumulation in the f32 instance, which is the only precision whose ms per step this spec reports as the training number and which replaces every derivation of how long the fine-tune takes.

## refutation condition

The ablation is refuted as a basis for deciding whether e3m2 can be trained into granite on this machine if any one of these observations holds:

- the AC13 relation `final held-out loss(qat) - final held-out loss(control) <= 0.05` prints `holds=false`; the 0.05 nats per token is a pre-registered gap, status plausible, not derived from any measurement in the tree;
- the AC13 relation `final held-out loss(qat) < final held-out loss(ptq_eval)` prints `holds=false` (QAT recovers nothing over quantizing after training);
- the AC11 identity control prints `within=false` (two fake-quant-off runs with the same seed disagree by more than 0.001 nats per token, so the run-to-run noise exceeds the effect being measured and every other relation is void);
- the AC15 token-agreement example prints `within=false` for the `qat` cell;
- AC1 prints a nonzero `metal_reject`, or AC3 prints a `step_bench_refused` line for 24 layers (the full model does not run on this GPU); these are recorded outcomes that move the work to the rejected ops or to a memory design, they are not failures of the measurement.

Any one refutes the relation it names. Refuting output is recorded, never edited. The throughput and memory numbers of AC3, AC16 and AC17 stand on their own whatever the quality relations print.

## architecture

The owner's two questions have one answer each, bound by reading, not by estimate.

How long: UNMEASURED. Every training record in the tree is a 32-parameter toy: two experts of `[4,4]` (`proxima-tensor/specs/low_precision_moe_training/SPEC.md:35`). The CPU pilots recorded `wall_time_ns` per step (mean 2,088,894 ns for the fp32 arm, 9,021,112 to 9,084,544 ns for the six packed arms, averaged over the step records of `proxima-tensor/specs/low_precision_moe_training/results/tiny-pilot.json` and `proxima-tensor/specs/packed_pilot_moe_training/results/packed-tiny-pilot.json` with `jq`), and the record keys of `proxima-tensor/specs/metal_packed_pilot_moe_64step/results/metal-packed-pilot-64step.json` hold 0 matches for wall, time, ms or rss. Nothing predicts granite; R3 measures it.

GPU: yes. `Differentiated.program` is an ordinary `proxima_tensor` program, and omega executes it on Metal through `execute_plan_named` (`proxima-tensor/specs/metal_packed_pilot_moe_64step/SPEC.md`, admitted, 64 steps). `proxima-autograd` has no Metal code and needs none: `git grep -i metal origin/main -- proxima-autograd` prints 0 lines. The backward is a graph transform (`proxima-autograd/src/adjoint.rs`, module doc) producing `Elementwise`, `Reduce`, `Input`, `Constant` and `Iota` nodes, so "Metal backward coverage" is whether omega's emit accepts every node of the adjoint program, which is the R1 census. Parts that stay on the host by existing design: the gathered-operand gradient, coalesced by `proxima_autograd::sparse::dedupe_and_sum_rows` (`adjoint.rs` module doc, `GatheredContribution`). CPU training is out of scope.

```
qat_census / qat_step_bench / qat_finetune / qat_relations   proxima-model-interop/examples/ (feature qat), shared module examples/qat/mod.rs (the tests under proxima-model-interop/tests/ include it through a path attribute, precedent omega/tests/packed_brain_float_moe_training_metal.rs:24)
  descriptor  = conflaguration::from_file(tests/fixtures/model-configs/granite_moe.toml), block_count overridden for the 1-layer cell
  forward     = proxima_tensor::spec::descriptor::build_forward(&descriptor).program        (descriptor.rs:679)
  loss        = proxima_autograd::loss::softmax_cross_entropy(logits, targets)
  step graph  = differentiate(program, loss)  -> Differentiated { program, gradients, gathered }
  per tensor selected by convert::policy_selects:   effective = Add(master_leaf, delta_leaf)      // STE, no new op
  delta       = fake_quant_program(master) - master       // Metal, store to the e3m2 layout and load back (float-layout-dtype path), evaluated before the step graph
  update      = proxima_autograd::optimizer::adam_step(...) then store(master', FloatLayout::BF16)          // Metal, the float-layout-dtype path (R2)
  masters     = bf16 buffers; activations bf16; accumulation (matmul, reduce, gradient buffers, Adam moments) f32
  ~~masters = f32 buffers holding bf16-grid values~~  struck 2026-10-11: an f32 buffer is 2x the bytes of the bf16 master it imitates and its ms per step is not the number a bf16 run produces
fake_quant (CPU function, the oracle)      proxima-gguf/src/quant/scaled_float.rs  quantize_block / dequantize_block, FloatLayout::E3M2
eval        = mean softmax cross-entropy over 64 held-out sequences of 256 tokens, step graph forward only
export      = masters -> F32 GGUF (transform writer);  convert_codec (policy default, fp6_e3m2) runs on the export
agreement   = codec_token_agreement (fp6-e3m2-codec slice 16), unchanged
```

Fake-quant is a function, `fake_quant_e3m2(values: &[f32]) -> Vec<f32>` over whole blocks, composed from `quantize_block` and `dequantize_block`; it wears the transform pipe form through the closure bridge in the example and adds no type to a library crate (R19). The pipe question for it: a transform `[f32] -> [f32]`, expressed as the function above. The second question (what can a caller do that they could not before) is answered by R6: the same transform as a Metal store to the e3m2 layout and a load back, which the CPU function cannot give.

### decisions

| decision | chosen | why not the alternative |
|---|---|---|
| STE as `Add(master, delta)` with `delta` a bound leaf | yes | an in-graph quantizer would be differentiated by the adjoint: `Greater` and `Equal` have no gradient (`adjoint.rs:602`) and `Reduce(Maximum)` mask-routes, so the gradient would be the quantizer's true derivative, not the identity; a leaf has no inbound derivative, so the existing `Add` rule is exactly STE and needs no stop-gradient op |
| fake-quant on Metal is a store to the e3m2 layout and a load back, through the float-layout-dtype path | yes | one encoder for every layout is the owner's frame (float-layout-dtype), and the ablation then measures the dtype system rather than a side codec; ~~fake-quant as a graph over existing `ScalarOp`s (`Reduce(Maximum)` absmax, an `Elementwise` of dtype `Float16` for the f16 scale, constant add and subtract for the grid)~~ struck 2026-10-11: it is a second e3m2 encoder beside the generic one. If R6 or R7 print a mismatch the recorded outcome is an emitter amendment in float-layout-dtype, not a looser bound |
| the masters and activations are stored in the BF16 layout and accumulation is f32, through float-layout-dtype; this spec waits on that spec's slice 19 | yes | Metal rejects every dtype but `Float32` and `Float16` outside a gather's indices (`omega/src/metal/prepare_uniforms_pack.rs:409`) and `type_token` renders `BFloat16` as `float` (`omega/src/msl/signature_tokens_prelude.rs:313`); bf16 weights reach Metal today only as packed `Codec::BFloat16` bytes widened at the read (`proxima-model-interop/src/expert_slab.rs:238`); MSL has a native `bfloat` type, Metal 3.1 and later (Metal Shading Language Specification v4.1 section 2.1, https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf, fetched with curl, HTTP 200, 14,564,497 bytes; this box is macOS 15.8, Xcode 26.3), and float-layout-dtype selects it by layout fields; an update smaller than half a bf16 ulp is lost in a true bf16 master exactly as in a grid, and R17 reports the memory |
| ~~`bf16` masters are the bf16 grid in f32 buffers~~ | struck | refused by the owner 2026-10-11: "why would you accept f32 when a) it's more expensive everywhere and b) we no longer have a real timing"; an f32 buffer costs 4 bytes where bf16 costs 2 on every master, delta and activation, and the ms per step it produces is the timing of a precision nobody trains in, so no number from it is the training number |
| learning rate 1e-4, no search | yes | Adam's first step is about the learning rate; a bf16 weight of magnitude below 0.03125 has half-ulp at most 6.1e-5, so 1e-4 survives rounding there, and a 1e-5 step would be lost for every weight above 0.0078; each run prints `updates_lost_to_rounding`, the count of elements whose master did not change while the Adam update was nonzero, so the loss is measured, not assumed |
| masters start from the Q8_0 checkpoint | yes | the fp32 original is not in the tree; the starting point carries Q8_0's error, stated in the result section |
| ptq arm is eval-only on the control's masters | yes | "recovers" needs the quantized-after-training baseline; it costs one evaluation, not a run; its checkpoint is `convert_codec` over the control export |
| exports are F32, not bf16 | yes | `convert_codec` sources are F32, F16, Q8_0 and Q4_0 (fp6-e3m2-codec R13); F32 holds the bf16 grid exactly |
| data order from `Lcg(seed)` | yes | the packed pilots use the same generator (`low_precision_moe_training/SPEC.md:35`); the order digest is printed so control and qat are compared by value |
| agreement cells reuse `codec_token_agreement` with the converted checkpoint on the fp6 side and the unconverted control export on the "shipped" side | yes | the example's gap is `shipped_match - fp6_match` against recorded ids; the llama ids are the common ground truth and the unconverted control is the reference the problem statement names, so the gap is what conversion costs after the fine-tune; the `ptq` cell supplies the no-QAT conversion and the `ctl` cell the control against itself |

## out of scope

- pretraining, any training that starts from random weights
- LoRA and every other parameter-efficient variant; the ablation trains the full selected tensors
- other codecs: a second codec is a parameter of `fake_quant` and the policy, not a new spec
- CPU training: the CPU pilots stay as they are, no CPU arm is added
- ~~a width-true bf16 master is out of scope (needs an omega `BFloat16` dtype path, `omega/src/metal/prepare_uniforms_pack.rs:409`); the grid-in-f32 master is the decision above~~ struck 2026-10-11: the owner refused the f32 interim ("why would you accept f32 when a) it's more expensive everywhere and b) we no longer have a real timing"); the omega bf16 dtype path is R2, slice 2, and precedes the throughput measurement
- fake-quant of activations or KV cache in any float layout; the training activations are bf16 and unquantized (R3), weights only are fake-quantized
- the 500 MB serving cap: lifted for training by the owner on 2026-10-11; it still binds serving
- any Ollama or llama-server run; the token oracle is the recorded llama ids and the control's own checkpoint
- changing the serving default of e3m2; the owner decides on the AC13 and AC15 outputs
- hyperparameter search, multiple seeds, learning-rate sweeps: one pre-registered setting, final-step checkpoint for every arm

## risks

| risk | likelihood | what it costs | what we do about it |
|---|---|---|---|
| the full 24-layer step does not fit this GPU's memory (bf16 masters and `delta` leaves, f32 gradient accumulators and f32 Adam moments; 18.2e9 bytes derived for 1.3 B parameters at the control, plausible, AC17) | unmeasured | AC3 prints `step_bench_refused` and no full-model fine-tune can run | the refusal names the failed allocation; the next work is a memory design from that record, not an estimate |

| Metal rejects ops in the granite adjoint | unmeasured; known gates are `ScatterNotSupported` (`omega/src/error.rs:79`) and the adjoint's own refusals `ScanAdjointUnsupported`, `NonProjectionOperandMap`, `ReduceOverGatherUnsupported` (`proxima-autograd/src/error.rs:29,52,71`) | AC1 prints a nonzero `metal_reject` | each rejected node line names the op; ops land as their own slices before slice 3, and TASKS is amended with the struck order |
