# float-layout-dtype

status: audited
owner: Brian Bruggeman
created: 2026-10-11

## problem

Every stored number in proxima (each `DType` float variant and each integer variant of at most 32 bits, and each of the 33 `Codec` variants of `proxima-primitives/src/codec.rs`) is today a named variant with decoder code of its own, and the owner's frame (2026-10-11) is "so when we build q*, or i* or whatever we've come up with that's new, we are literally just one more type of configured byte": this spec makes each of them an instance of one configured layout (the `FloatLayout` struct of `proxima-primitives/src/float_layout.rs:20`: sign, exponent bits, mantissa bits, specials, bias, extended by a sign encoding, a block descriptor and a codebook), rendered by one CPU codec and one omega emitter, measured by: bit-exact parity of every layout against the recorded output of the decoder it replaces on real granite 3.1 1b A400M and gemma4 E2B rows, the per-name and per-codec arm censuses reaching 0 outside the one tag table, an unnamed layout (3-bit integers under an f16 scale, 32 per block) running on CPU and Metal with zero new code, and, at the end of each family, a top-1 agreement rate of at least 0.95 against the recorded llama ids on both models (~~byte-identical recorded llama ids~~ struck: byte-exact model responses are the wrong correctness bar (owner 2026-10-11: "we cannot really judge responses even from the same model on the same stack"); exactness applies only where the arithmetic is exact; decoders and stage records stay bit-exact).

## refutation condition

The claim "one configured layout covers every stored number" is refuted by any one of these observations:

- a parity AC (AC6, AC13, AC14, AC15) prints a mismatch above 0 that survives the amendment named in the risks table: some stored number then needs decode code that is not a configured layout, and the layout struct is missing a field;
- the AC16 unnamed-layout test needs a new line of non-test source in `omega/src`, `proxima-gguf/src` or `proxima-tensor/src` to run (its scan of those sources for the layout's name prints a hit, or its census line prints a nonzero arm count);
- the codec census (R1) finds a `Codec` variant whose element decode is neither field arithmetic nor a codebook lookup (the two shapes this spec admits);
- AC11 or AC16 prints a per-name or per-arm count above 0 after its slice: a name-keyed code path survived the migration.

Refuting output is recorded, never edited. Hardware outside this box (CUDA, wgpu) is covered by text-emission tests only and says so in AC9; no claim about it stands on a parity run.

### the shapes

```
element       FloatLayout { exponent_bits, mantissa_bits, specials, bias_override, sign }   // sign added by R12: Absent | Magnitude | TwosComplement; offset-binary bias K added beside it by R12 (Q4_0 is code - 8)
              uint  = exponent_bits 0, sign Absent                 (mantissa only)
              int   = exponent_bits 0, sign Magnitude | TwosComplement, bias_override Some(1 - mantissa_bits) so the scale is exactly 1
block         BlockLayout { elements, planes (bit planes of an element: nibble + high-bit array, ql + qh), element-to-sub-block map, skipped bytes, scale: FloatLayout, min: Option<FloatLayout>, sub: Option<nested BlockLayout> }
codebook      Option<table constant>: scalar (Iq4Nl) or vector with a sign table (Iq2Xs, Iq3Xxs); decode is field arithmetic OR a table lookup, never anything else
codec         Codec stays the 33-value wire tag (tags 0..32 never change); Codec::layout() is the one table from tag to configured layout
omega         one emitter: native MSL type when the fields equal one (float, half, bfloat), else field arithmetic, else table lookup
cpu           proxima-gguf quant::float_layout::{encode,decode} + one block walker over BlockLayout
```

Consequence, stated because it is the point: a new `q*` or `i*` is a constant of the struct plus its parity fixture and zero kernel code (R16 proves it with a layout nobody named). The block-scaled integer quants (Q8_0, Q4_0: integer element under a shared f16 scale) have the same shape as the fp6 e3m2 blocks (float element under a shared f16 scale): one element layout and one block descriptor each.

What the census says about the struct. Distinct sign or offset encodings found in opened decoders: IEEE sign bit; two's complement (Q8_0, Q8_1, Q8K); unsigned with a separate min or offset (Q4_1, Q5_1, Q2K, Q4K, Q5K); offset-binary with K = 8, 16, 32, 1 and 4 (Q4_0, Q5_0, Q6K, Q2_0, Q3K); sign-only (Q1_0); a signed table value (Iq4Nl); a magnitude table times a sign table (Iq2Xs, Iq3Xxs). Distinct scale layouts: one f16 per block; f16 plus f16 min; f32 (Q8K); f16 plus packed sub-scales of 4, 6 and 8 bits with and without a min; E8M0 and E4M3 (Mxfp4, Nvfp4, doc comments only). Four features beyond the first sketch of the struct are therefore required and are named here, not discovered later: an offset-binary bias for integer elements (R12 adds it beside the sign encoding); element storage as bit planes (a nibble plus a high-bit array for Q5_0, Q5_1, Q5K, a 2-bit plus a 1-bit plane for Q3K, `ql` plus `qh` for Q6K) with an element-to-sub-block map that is not a plain stride (Q4K, Q2K, Q6K lane interleave); skipped bytes (Q8_1, Q8K); and a vector-valued codebook (Iq2Xs, Iq3Xxs, one stored code selecting 8 or 4 elements and a sign mask from a second table). The element decode therefore has three shapes, all named by the struct: field arithmetic, scalar codebook, vector codebook with a sign table.

Findings that move a gate (read, not executed): `bf8_e5m2_element` (`omega/src/msl/kernel_types_identity.rs:1577-1586`) has no exponent-31 case and decodes it as a normal number, while the CPU decode treats exponent 31 as reserved (`proxima-gguf/src/quant/float_layout.rs:171-175`, `proxima-tensor/src/bfloat8.rs:114`): codes 0x7C to 0x7F and 0xFC to 0xFF disagree between the two incumbents. The CPU codec is the oracle for the layout (AC3 enumerates every code against an independent f64 reference), so the replacement emitter follows the layout's `Specials`; AC6 prints those eight codes' result. `BFloat8` and `Bf8E5M2` are two decoders for one set of fields differing only in `specials` (`InfinityOnOverflow` against `SaturateOnOverflow`), which is the struct's case for itself.

### decisions

| decision | chosen | why not the alternative |
|---|---|---|
| `DType` carries a `FloatLayout` for floats and for integers of at most 32 bits | yes | `dtype.rs:8-13` says every variant is "plain and fieldless" and keeps Decimal out as a payload-carrying variant; that stance is overturned for layouts, not for decimals, because a layout is an OPEN set (E4M3, int3, any future format) that a fieldless enum cannot name, and the owner's frame is one implementation for all of them; the old doc lines are struck in the slice that lands this, with this reason |
| keep `DType` fieldless and carry a `FloatLayout` beside it on every `Op` | no (abandoned) | every `Op` and every omega buffer descriptor would carry two fields that must agree; the disagreement is a bug class the single carrier removes; the same reasoning as `Codec` being a wire tag beside layouts is why `Codec` stays a tag |
| named constants (`DType::Float32`, `DType::BFloat16`, ...) kept as associated constants | yes | expression sites (the bulk of the 2,165 lines in proxima-tensor) keep compiling and read the same; pattern sites that select behavior by name are the census's `pattern_sites` and are rewritten to fields |
| hardware type chosen by comparing layout fields, never by name | yes | `half` and `bfloat` are layouts that happen to have a hardware type (`bfloat`: Metal Shading Language Specification v4.1 section 2.1, Metal 3.1 and later, https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf, fetched with curl 2026-10-11, HTTP 200, 14,564,497 bytes; this box is macOS 15.8, Xcode 26.3); a name check would be a second place to forget an instance |
| `Codec` stays as the 33-value tag and gains `layout()` | yes | tags 0..32 are an on-disk sidecar wire format (`codec.rs:6-9`); deleting the enum breaks files, so the enum shrinks to a tag table and every decode arm is removed |
| the block descriptor is a struct (`BlockLayout`) | yes | pipe question answered by writing the expression: with `FloatLayout` alone, "32 elements of E3M2 under an f16 scale" has no place to put 32, the scale layout or a nested sub-block; 33 `Codec` variants and their per-codec files are the compensators for exactly this missing struct |
| codebook decode as a constant of the same struct | yes | IQ4_NL and the IQ family decode an index through a table, not sign/exponent/mantissa arithmetic; the element decode therefore has two shapes (field arithmetic, table lookup) and the struct names which, with the table as data; this is the one structurally justified exception, and it is a constant, never a code path per IQ variant |
| parity oracle is the recorded output of the incumbent decoder, not the new code | yes | the decoders being replaced are the incumbent; the recorder (R1) writes their output on real rows to vendored fixtures before any slice replaces them, so a deleted decoder still has an oracle; the independent oracles (f64 reference, `half`, recorded llama ids) check the codec itself in R3 and the end of each family |
| Float64, Int64, UInt64, Int128, UInt128 stay named | yes | the generic codec's intermediates are `u32` ("layouts are at most 32 bits wide", `float_layout.rs` module doc); widening it is a different change |

Designs abandoned by applying the constraints: one `Bf4`/`Bf6` Metal arm per width (the bf16-only dtype path first drafted for the QAT ablation), which the owner's "why do we have a bf16/32/etc. implementation" removed; a fieldless-enum-plus-sidecar-layout carrier, abandoned above.

## out of scope

- Float64, Int64, UInt64, Int128, UInt128: wider than the generic codec's 32-bit bound
- running CUDA or wgpu on hardware: this box has neither; AC9 is text emission only and no parity claim is made
- the fp6 e3m2 codec work itself (`proxima-tensor/specs/fp6-e3m2-codec`), the QAT ablation (`proxima-tensor/specs/fp6-qat-ablation`, which depends on the last slice of this spec), and any change to a serving default
- performance tuning of packed matvec kernels (`*_pair_dot`, row-blocked and tiled variants): they stay as kernels; this spec removes decode code keyed by name, and a kernel that is faster than the generic path stays, selected by fields; their measured numbers are the owner's call
- changing any on-disk tag: tags 0..32 are wire format
- training dynamics: the ablation, not this spec, measures what a layout does to training

## risks

| risk | likelihood | what it costs | what we do about it |
|---|---|---|---|
| the generic codec mishandles `exponent_bits = 0` (integers): `exponent_ones` is 0 and every code is subnormal | unmeasured; the integer slice (R12) is the first to run it | AC12 prints a mismatch above 0 | the fix is in the generic module's field arithmetic, not an integer special case; a failing code is printed with its decoded value beside the native cast |
| MSL encode by bit arithmetic disagrees with the CPU encode on ties or at saturation | medium | AC6 mismatch above 0 | amend the emitter to the CPU algorithm's integer steps; the bound is not loosened |
| `DType` carrying a payload loses `Copy`-sized simplicity or its serde spelling | low; `FloatLayout` derives `Debug, Clone, Copy, PartialEq, Eq` | AC2 round-trip fails | the former spellings are kept by explicit serde mapping, asserted in AC2 |
| the block descriptor cannot express a K-family nesting without a code path | unmeasured; the family census table is the check | AC14 `descriptors_state_sub_block_fields` fails | the descriptor gains the missing field; a variant that still needs its own code path is recorded as the refutation of R14, not hidden |
| offset-binary elements (Q4_0 stores code minus 8), split high bits (Q5_0 `qh`) and packed sub-scales are not sign, exponent or mantissa | medium; read from the decoders by the R1 census | the element layout needs a bias or storage-geometry field | the field lands in the same struct with its parity fixture; never a per-codec branch |
| 237 tests is more than one slice's budget | certain | slices run long | each family slice may split by codec with the AC kept on the last part; TASKS records the split |
| ten codecs have no decoder to be an incumbent (Iq1S, Iq1M, Iq2Xxs, Iq2S, Iq3S, Iq4Xs, Tq10, Tq20, Mxfp4, Nvfp4) and no libggml exists on this box | certain: `dispatch.rs:37,59-61` return `UnsupportedCodec`; `/opt/homebrew` and `~/repos` hold no llama.cpp or libggml (searched 2026-10-11) | their layout constants cannot be written from a decoder, and ggml cannot be linked: it is the oracle and incumbent, recorded once, never a dependency | each constant is written from the ggml format (`types.rs:404-415` geometry plus ggml's own source) and checked against ggml's f32 decode of N real blocks (N at least 4) vendored under `proxima-gguf/tests/fixtures/ggml-decode/<codec>/`, recorded once with llama.cpp's own tooling as an external tool (README names tool, exact command, ggml commit, source tensor; a public GGUF by HF repo, file, tensor and byte offset where the box holds none); AC17 runs only the proxima decode against the vendored f32; until AC17 prints 32 the 10 stay unexplained in the result |
| the MSL incumbent `bf8_e5m2_element` decodes exponent 31 as a finite number while the CPU decode treats it as reserved (`kernel_types_identity.rs:1577-1586` against `quant/float_layout.rs:171-175`) | read, not executed | eight codes (0x7C to 0x7F, 0xFC to 0xFF) change value on the Metal path | the layout's `Specials` decides; AC3 shows the CPU side against the f64 reference, AC6 enumerates these codes as `float_layout_parity_bf8_e5m2_exponent_31_specials_msl_equals_cpu`, and the change is recorded in the result, not hidden |
